## (a) 진짜 문제 — 1건

### N-1. `publish_stuck` 스코프와 술어가 **시계를 따로 읽는다** — **GREEN (영향 미미)**

**Codex 지적** `[논리 오류][확신도 낮음]`: 스코프는 `now`·`cutoff` 를 쿼리 생성 시점에
바인딩하고, 술어는 호출 시점에 `Time.current` 를 다시 평가한다. 경계에 걸친 레코드가
두 호출 사이의 시간 차이로 갈릴 수 있다.

**측정해서 확인했다 — 그리고 지적보다 한 겹 더 있다.** 스코프 **내부**에서도 시계를
두 번 읽는다:

```
now    = 2026-09-17 17:39:48.965094
cutoff = 2026-09-16 15:39:48.965133
cutoff + 26h - now = 3.9e-05 s     ← 0 이어야 하는데 39 마이크로초 벌어진다
```

`now: Time.current, cutoff: Time.current - grace` 가 `Time.current` 를 **두 번** 호출하기
때문이다(`app/models/post.rb:76`). 술어는 또 따로 읽는다(`:82`, `:84`). 두 구현을 합쳐
**시계를 네 번** 읽는다.

**GREEN 인 이유**: 26시간 창과 **하루 한 번 도는 잡**에 대해 39마이크로초는 어떤 판정도
바꾸지 않는다. 실제로 갈리려면 `published_at` 이 그 마이크로초 구간에 정확히 들어와야 한다.
우리가 둔 8개 조합 대조 테스트도 이 정밀도에서는 갈리지 않는다(통과 중).

**그래도 (a) 로 세는 이유**: 스코프 하나 안에서 `cutoff` 가 `now - grace` 가 **아닌** 것은
의도와 다른 코드다. 근거가 "차이가 너무 작아 괜찮다" 인데, 그건 이 저장소가 반복해 당한
"암묵적 상류 의존" 과 같은 종류의 근거다 — 값의 성질이 아니라 값의 크기에 기대고 있다.

**예상 수정 범위** (다음 런): 시계를 **한 번만** 읽고 넘긴다 —
`scope :publish_stuck, ->(grace = PUBLISH_GRACE, now: Time.current) { … cutoff: now - grace }`
와 `def publish_stuck?(grace = PUBLISH_GRACE, now: Time.current)`. 부수 효과로 **테스트가
시각을 고정할 수 있게 되어** 경계값을 마이크로초 단위로 단언할 수 있다(지금은 못 한다).

## 이번 라운드에 우리가 스스로 잡은 것 (Codex 지적과 별개)

리뷰가 도는 동안 ⑦.3(파생 상태가 놓치는 경우)을 직접 파보다 **실제 결함**을 찾았다:

**증상**: 잡이 거부한 글을 사람이 어드민에서 고쳐도 `publish_error` 가 남아,
배너가 이미 해결된 실패를 계속 설명한다. 재현(실측):

```
after failure  : stuck=true  reason="…본문(한국어)을(를) 입력해 주세요"
after admin fix: stuck=true  reason="…본문(한국어)을(를) 입력해 주세요"   ← 거짓
                 body=18b                                             ← 본문은 채워져 있다
```

**수정**: `before_save :clear_stale_publish_error, if: -> { publish_error.present? && changed? }`.
기록된 이유는 "잡이 시도한 시점의 레코드" 를 설명하므로, 사람이 편집하면 그 설명은 거짓일 수
있다. 지우면 글은 여전히 `publish_stuck` 에 남되(아직 지났고 아직 예약이다) **유예 창으로
되돌아간다** — 증거가 사라졌으니 다음 런을 다시 기다리는 게 정직한 상태다.
잡은 `update_column` 으로 쓰고 지우므로 이 콜백과 같은 필드를 다투지 않는다.
테스트 3개 추가(지워짐 / 지워도 진짜 지연은 유지 / 변경 없는 저장은 그대로).
