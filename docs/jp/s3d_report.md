## 1. 무엇이 틀렸나

승격 조건 자체는 S3c 가 요구된 대로 두 겹이었다 — 「직전 페이지가 그 카드의 `front`」
∧ 「이 페이지가 `JP_BACK_ANCHORS[doc]` 에 맞는다」. 틀린 것은 **두 번째 겹의 증명력**이다.

```js
const JP_BACK_ANCHORS = { mynumber_card: /個人番号|マイナンバー|二次元コード/, … };
```

- `二次元コード` 는 **카드 고유도 아니고 뒷면 고유도 아니다.** 資格確認書에도 있고,
  택배 전표에도 있고, QR 안내 전단에도 있다.
- `マイナンバー` 는 이 카드에 **관해 쓰인 모든 안내문**에 있다.
- 즉 이 앵커는 「이 페이지는 그 카드의 뒷면이다」를 입증하지 않고
  **「이 페이지는 그 카드를 언급한다」**를 입증한다. 둘은 다른 명제다.

직전 라운드의 양성 케이스(`表 + 裏(タイトル切除) → 裏面に昇格`)는 이 결함을 잡지 못한다 —
**옛 앵커에서도 새 증명에서도 똑같이 통과**하기 때문이다. 잡으려면 「옛 앵커 단어를 갖고
있으면서 뒷면이 아닌 페이지」가 필요하다(§2-B).

## 2. 수정

### A. 단어 대신 **복합 증거** — `JP_BACK_PROOF` (`public/safe/index.html:1252`)

각 카드가 「레이블 ∧ 그 면 고유의 값 형식」 둘을 함께 입증해야 승격된다. 그리고
값 형식은 **골든이 이미 돌리는 그 탐지기**로 확인한다 — 두 번째 병렬 파서를 만들면
본 탐지기와 조용히 어긋난다.

| 문서 | 레이블 | 그 면 고유 값 형식 |
|---|---|---|
| `mynumber_card` | `個人番号`·`マイナンバー` 가 **세그먼트 머리**에 | 그 뒤 **12자리 숫자** (`jpDigitSpan(seg, L.end, 12, jpTailEnd(…))`) |
| `unten_menkyo` | `備考欄`·`臓器提供`·`提供意思`·`意思表示欄` | 그 밑의 **그려진 欄 프레임** (`jpFrameBelow`) |

- **전각·4-4-4 구분은 이미 처리된다.** `jpNorm` 의 NFKC 가 전각 숫자를 접고,
  `jpDigitSpan` 이 `[\s.\-・,/]` 구분자를 허용한다. 카드가 실제로 인쇄하는 모양이
  `1234 5678 9012` 이므로 이 둘이 없으면 양성 케이스가 깨진다.
- **`二次元コード` 단독·`マイナンバー` 단독 승격은 사라졌다.** `マイナンバー` 는 레이블
  자리로는 남아 있지만 **12자리가 없으면 아무 일도 하지 않는다**(§2-B 의 ② 가 그것).
- **免許証은 「단어 + 픽셀」로 조였다.** 전단은 `備考欄` 이라는 단어를 인쇄할 수 있지만
  免許証 뒷면을 이루는 **150px 연속 잉크 가로줄의 사각 프레임**은 인쇄하지 않는다.
- **資格確認書·住民票은 의도적으로 항목이 없다.** 양면 카드가 아니고 `jpClassify` 가
  이 둘에 `side` 를 부여하지 않는다 — 스스로 이름을 못 대는 페이지는 아무 규칙도 받지
  않는 것이 정답이다. (「조였다」가 아니라 「애초에 없다」가 맞는 상태임을 확인한 것.)
- `臓器提供` 가 `mynumber_card` 항목에 없는 것은 그대로다 — マイナ에서는 **앞면** 항목이다.

### B. 음성 테스트 3개 — **합성, 바이너리 미커밋**

새 조건은 **두 겹의 논리곱**이므로, 음성 케이스도 겹마다 하나씩 있어야 한다.

| # | 2페이지 내용 | 깨는 겹 |
|---|---|---|
| ① | `二次元コードのご案内 … お問い合わせ受付番号 999988887777` | **값 형식은 있고 레이블이 없다** |
| ② | `マイナンバーのご案内 … 提出先の案内をご確認ください。` | **레이블은 있고 12자리가 없다** |
| ③ | ① 과 같은 안내문을 **흰 캔버스에 그려** front.png 와 함께 PDF → **OCR** | 실제 스캔 경로 |

- ①② 는 앱 자신의 텍스트 렌더러(`loadFromText`) 로 만든다 — 페이지 텍스트가 케이스에
  적힌 그대로여서 **OCR 변수가 섞이지 않는다**. 빈 줄 60개로 페이지를 끊고,
  「2페이지인가」를 가정하지 않고 **단언**한다(`JP_NEG_PAGES`).
- ③ 은 `buildPdfFromImages` 에 `{text}` 소스를 추가해 런타임에 합성한다.
  **새 바이너리는 저장소에 들어가지 않는다**(`out/gen/` 은 gitignore).
- 단언: 2페이지 class **`null`** · `viaBackAnchor` **false** · 2페이지 JP 엔티티 **0** ·
  `back_all` 띠 **0** · 2페이지 피복 **≤10%**, 그리고 **1페이지는 여전히
  `mynumber_card/front` 이고 자기 필드를 갖는다**(프리셋이 통째로 무너져서 「2페이지에
  아무것도 없다」가 참이 되는 경로를 배제).

**`JP_NEG_VACUOUS` — 이 음성 테스트가 공허해지는 경로를 먼저 막았다.**
「승격되지 않았다」는 **옛 앵커 단어가 애초에 페이지에 도달하지 않았을 때도 참**이다
(크롭 실수, OCR 실패, 렌더러 변경). 그래서 **옛 정규식 `/個人番号|マイナンバー|二次元コード/`
가 2페이지 텍스트에 여전히 맞는다**는 것을 함께 단언한다. 이 줄이 녹색인 동안에만
나머지 단언이 새 규칙에 대한 증거다. 측정: 3케이스 모두 `match` — **OCR 경로(③)에서도
안내문이 읽혔다**(읽히지 않았다면 이 줄이 빨개진다).

### C. 안내문이 `マイナンバーカード` 를 쓰지 못하는 이유 (측정으로 확정)

지적서의 예시 문구는 「マイナンバーカードの二次元コードについて…」였는데, 그 문자열은
`JP_CLASSES.mynumber_card` 에서 `マイナンバーカード`(4) + `マイナンバー`(2) = **6점**으로
**스스로 카드로 분류된다**. 그러면 승격 경로에 도달하지 않으므로 이 AMBER 를 재현하지
못한다. 그래서 안내문은 `二次元コード` / `マイナンバー` 만 쓴다(각 0점·2점, 둘 다 min 4 미만,
타이틀 키워드 아님 → class `null`).

⚠ **이것은 별개의 공백이다**: 산문이 카드 이름을 쓰면 분류기가 그 페이지를 카드로
간주한다. 이번 범위 밖이라 손대지 않았고 §5 백로그 D-1 로 남긴다.

## 3. 변이 프로브 (실측)

앵커를 옛 정규식으로 되돌리고(`JP_BACK_PROOF` 분기를 `JP_BACK_ANCHORS` 정규식 테스트로 교체)
전체 골든을 재실행했다. 되돌린 뒤 원복했고 원복 후 557/557 을 재확인했다.

```
TOTAL: 542/557 pass, 15 FAIL   — 새 음성 3케이스가 전부 빨강 (케이스당 5건)
JP_BACKANCHOR   page 2 promoted   false → true      (①②③ 모두)
JP_ATTACH_CLEAR page 2 coverage   <=10% → 100%      (①②③ 모두 — 안내문 전면이 띠로 덮인다)
```

즉 이 테스트는 **지적된 결함을 직접 되살려 잡는다**. 함께 빨개진 나머지:
`JP_PAGECLASS`(`null` → `mynumber_card/back`), `JP_ENTITIES`(2페이지 0 → 3·1·4),
`JP_BACK_ONLY`(`[]` → `[1]`). 양성 케이스(`表 + 裏(タイトル切除) → 裏面に昇格`)는
변이 전·후 **양쪽에서 통과** — 그것이 §1 에서 「양성만으로는 못 잡는다」고 적은 이유다.

### 免許証 뒷면 승격 경로의 도달성 — 측정했고, **도달하지 않는다**

`JP_BACK_PROOF.unten_menkyo` 를 조이면서 「골든이 이 경로를 돌고 있나」를 확인했다.
免許証 뒷면을 タイトル만 크롭해 2페이지로 묶어 실측한 결과:

```
pageCls : [ unten_menkyo/front sc=9 , unten_menkyo/front sc=4 ]
jpClassify(1) 단독 : unten_menkyo/front sc=4     ← 스스로 분류된다 → 승격 경로 미도달
jpBackProofFrame(1) : true                        ← 조인 증명은 진짜 뒷면을 받아들인다
```

두 가지가 동시에 사실이다: ① **조인 증명은 실제 免許証 뒷면에서 참이다**(직접 호출로 확인) —
과잉 조임이 아니다. ② 그런데 **그 경로는 돌지 않는다** — 免許証 뒷면은 `備考欄`(2) +
`臓器提供`(1) + `提供意思`(1) = 4점으로 **자기 힘으로 분류되고**, `side` 판정에는 免許証용
뒷면 증거가 없어 `裏面` 글자가 크롭되면 **`front` 로 떨어진다**.
그래서 이번에 免許証 양성 케이스를 골든에 넣지 **않았다** — 넣으면 「뒷면을 front 로 읽은
상태」를 골든에 고정하게 된다. 그 side 판정 공백은 §5 백로그 D-2 다.
(마스킹 자체는 유실되지 않는다: `JP_REGION_LABELS` 는 side 로 필터하지 않으므로
`biko_change`·`organ_donor` 띠는 그대로 적용된다 — 확인함.)

## 5. 남는 공백 (다음 런 — 배포 후)

이번 라운드가 만든 것:
- **D-1** 산문이 `マイナンバーカード`·`個人番号カード` 를 언급하면 그 페이지가 **카드로 분류된다**
  (4점 단일 키워드). 승격 경로와 무관하게 분류기 자체의 과잉 발화이고, 이번 음성 테스트의
  문구 선택을 제약한 원인이다(§2-C). 분류에 「서식 구조」 조건을 더할지가 제품 판단.
- **D-2** `unten_menkyo` 의 `side` 판정에 **뒷면 고유 증거가 없다** — `裏面` 글자가 없으면
  `front` 로 떨어진다(§4 실측). `jpBackProofFrame` 을 side 판정에도 쓰면 닫히지만,
  그러면 단일 페이지 免許證 뒷면의 side 가 바뀌어 기존 골든 기대표가 움직인다.
- **D-3** `JP_BACK_PROOF.mynumber_card` 는 12자리의 **체크디지트를 보지 않는다**. 보게 하면
  알파 카드 더미(의도적 무효 번호)가 승격되지 않아 양성 케이스가 깨진다 — 더미의 번호
  유효화(CLAUDE.md JP-1 이슈 로그의 후속 작업)와 **한 묶음**이다.
