# SafeFile golden-fixture tests

Automated regression gate for the PII detection/redaction pipeline in
`public/safe/index.html`. Instead of fixing symptoms one document at a time,
this encodes the **expected result** for a set of trap documents as a spec, then
verifies the *live* page against it headlessly. **Run it after every change to
the SafeFile pipeline and keep it green.**

## What it checks

For each fixture, `specs.json` declares:

| Field | Meaning |
|-------|---------|
| `must_mask` | value MUST end up geometrically covered by a mask rect |
| `must_not_mask` | value must NEVER be covered (schools, orgs, countries, place names) |
| `never_candidate` | value must not even be *proposed* as a review candidate (e.g. `Korea`) |
| `should_candidate` | value must surface as a visible candidate (top name, address) |
| `name_bar` | a large-name band hugs the glyphs (no ink exposed, not oversized) |
| `min_auto` / `max_auto` | regression floor / ceiling on the auto-detected entity count |
| `out_formats` | build the output in these formats and run the safety probes below |
| `ai_inject` | adversarial AI labels are neutralised in `addEntities` (no live API needed) |

### Output safety

What the user ships is the output file, not our preview, and a redacted-looking
file can still carry the original three different ways. Each needs its own probe
— pdf.js text extraction catches only the first:

| Leak | Probe |
|---|---|
| text layer under the ink ("透ける黒塗り") | re-parse the PDF: **0 extractable characters** |
| metadata the renderer never shows | byte scan: image EXIF / XMP / IPTC, PDF `/Annots` `/EmbeddedFile` `/XFA` `/AcroForm` |
| incremental save (revision 1 — unredacted — still physically in the file) | byte scan: exactly **one** `%%EOF` |

An embedded ICC profile is allowed but bounded: Chrome attaches a 456-byte
generic sRGB profile (a colour space, not an identifier), while a *display*
profile would carry device manufacturer/model tags — so the probe caps size and
rejects `dmnd`/`dmdd`.

### Japanese documents (JP-1)

`jp_docs` replays each Japanese fixture's own `specs.json` — a box table in PNG
pixels plus, per 提出目的, which boxes that purpose hides / recommends / offers /
keeps — against the live pipeline:

| Category | Meaning |
|---|---|
| `JP_CLASS` | the page classified as the expected document (and face) |
| `JP_MASK` | a box the legal matrix marks `auto`/`auto_with_purpose_gate` is covered |
| `JP_MASK_OR_CAND` | 個人番号: banded **or** surfaced (see below) |
| `JP_CANDIDATE` | a `recommend` box surfaced as a review item |
| `JP_OPTIONAL` | an `optional` box is offered **and left clear** by default |
| `JP_KEEP` | a box the recipient needs is not grazed (≤10% covered) |
| `JP_FIELD` / `JP_BANDED` | the field was found / is actually banded (the only assertion a rotated phone-photo fixture can make) |
| `JP_COVERAGE` | **how many boxes this case actually checked**, and which keys it skipped |

Two things worth knowing before changing them:

- **Which assertion a box gets comes from the legal matrix level, not from which
  list the fixture put it in.** A purpose's `mask` list holds everything it
  hides, at both the automatic and the recommended strength, and those are
  different promises. `jp_auto_fields` in `specs.json` carries that mapping so
  the harness derives it independently of the app it is testing.
- **個人番号 is `mask_or_candidate`, on purpose.** Strategy v2 §4 requires every
  dummy's number to FAIL its check digit (generating a valid one is forbidden),
  so a correct implementation must refuse to assert "this is a 個人番号" and
  demote the automatic band to a default-ON review candidate. Asserting a hard
  band would make the golden reward the wrong behaviour; asserting only a
  candidate would let "never detected it" pass.

`JP_COVERAGE` exists because a harness that quietly checks zero boxes prints the
same green as one that checked forty. It caught a real counting bug in itself
within minutes of being added.

The `ai_inject` block reproduces the real-document false positives (an AI
labelling `Maharaja Agrasen College` / `Concern India Foundation` as a person's
name, or `Korea` / `Indian` as an address) **without** calling the paid AI
endpoint — it feeds those exact labels straight into the detection layer and
asserts they are demoted to visible or dropped.

## Fixtures (synthetic — no real personal data)

`generate_fixtures.py` (pymupdf + Pillow) writes to `testdocs/` (git-ignored):

- `1_text` `2_scanned` `4_table` `5_multipage` — Korean base docs (regression)
- `3_photo.jpg` — OCR path
- `6_resume_light.pdf` — single-column Indian résumé
- `7_resume_dark.pdf` — 2-column light/dark Indian résumé reproducing every trap:
  48pt serif name, `+91` phone, wrapping address, standalone `Korea`,
  `(Koreaz Contest)`, multiple schools, a body-prose org (`Concern India
  Foundation`), and a dark-green column (contrast/background test).

`fixtures/jp/` (committed, generated by `fixtures/jp/gen.py`) holds the four
Japanese alpha documents — 資格確認書 ×3 issuers, 運転免許証 表/裏,
マイナンバーカード 表/裏, 住民票 ×4 variants — each as `.png` (scan), `.jpg`
(phone photo: rotated, blurred, darkened) and `.pdf`. They are **non-realistic
schematic dummies** per strategy v2 §4: no logos, no official seals, no real QR,
invalid check digits, impossible addresses, and a permanent
「見本・架空・本人確認に使用不可」 overlay. All of them reach detection through
OCR, watermark and all — which is the point: it is the state a real phone photo
arrives in.

## Running

```bash
cd test/safe
npm install                 # playwright (chrome channel)
python3 generate_fixtures.py   # regenerate testdocs/ (needs pymupdf, pillow)
node run.mjs                # exit 0 = all pass; --only 7_resume_dark.pdf to focus
node run.mjs --only jp/juminhyo/zenin_mynumber.png    # JP fixtures use their path as the id
```

`render.mjs` writes the **composed output** of a fixture to `out/` so a human can
see where the bands landed. It is an inspection aid, not a gate — a coverage
fraction says how much is covered, only the picture says *where*. Both defects
found during JP-1 (a 保険者番号 digit surviving by 7px at 96% coverage, a
二次元コード band offset off the printed block at 80%) were invisible to the
numbers:

```bash
node render.mjs identity_submit fixtures/jp/shikaku_kakuninsho/kenpo.png
```

Requires Google Chrome installed (Playwright launches it via `channel:'chrome'`).
A JSON report is written to `out/report.json`.
